# Sana AI Technical Bible - Part 4: Backend & Database (Supabase)

Sana AI relies entirely on Supabase for its backend infrastructure. This eliminates the need to build and maintain a custom Node.js/Express server.

## Part 9 — Supabase Ecosystem

### 1. Authentication
**How it works:** We use Supabase Auth for user identity. When a user logs in (e.g., via Google OAuth), Supabase issues a JWT (JSON Web Token).
**Where it is used:** `src/integrations/supabase/auth-middleware.ts` and `auth.tsx`. The token is stored in the browser and automatically attached to every database request.

### 2. Realtime
**How it works:** Supabase allows subscribing to database changes via WebSockets.
**Where it is used:** In Study Together groups, if one user adds a resource or completes a topic, `supabase.channel('public:group_timeline').on('postgres_changes', ...).subscribe()` listens for those inserts and updates the UI instantly.

### 3. Row Level Security (RLS) & Policies
**How it works:** RLS applies security rules directly at the database level.
**Where it is used:** In `supabase_schema.sql`, we write policies like `CREATE POLICY "own notes all" ON public.notes USING (auth.uid() = user_id);`. This guarantees that even if a malicious user tries to query all notes, Postgres will only return notes where the `user_id` matches their auth token.

### 4. Database Triggers & Functions
**How it works:** Code that runs automatically on the database server when certain events happen.
**Where it is used:** We have a trigger on `auth.users` (managed by Supabase Auth). Whenever a new user signs up, the trigger `handle_new_user()` automatically executes and creates a corresponding row in our `public.profiles` table. We also use triggers to update `updated_at` timestamps automatically.

## Part 10 & 18 — Complete Database Architecture (PostgreSQL)

Our database is heavily relational. Here are the core tables and how they connect.

### 1. User & Profile Data
*   **`profiles`**: The central user record.
    *   *Columns:* `user_id` (Primary Key, Foreign Key to `auth.users`), `display_name`, `level`, `xp`, `focus_score`.
*   **`onboarding_preferences`**: Stores the user's selected study style and AI personality.

### 2. Revision & Learning Materials
*   **`revision_sets`**: A container for a study session or topic.
    *   *Columns:* `user_id`, `subject_id`, `progress_pct`.
*   **`notes`**: Markdown notes generated by AI or the user.
    *   *Relations:* Belongs to a `revision_set` (`set_id` Foreign Key).
*   **`flashcards`**: Spaced repetition cards.
    *   *Columns:* `front`, `back`, `mastery`, `last_reviewed_at`.
*   **`weak_areas` & `quiz_questions`**: Generated by AI to test the user's knowledge.

### 3. AI & Chat Memory
*   **`chat_threads`**: Represents a conversation session.
*   **`chat_messages`**: The actual messages within a thread.
    *   *Columns:* `thread_id` (Foreign Key), `role` (user or assistant), `content`.
*   **`study_notes`**: Structured JSON notes extracted from chat messages.

### 4. Third-Party Integrations
*   **`classroom_connections`**: Stores Google OAuth tokens for Classroom API.
*   **`classroom_courses`, `classroom_coursework`, `classroom_documents`**: Mirrored data from Google Classroom to avoid hitting API limits.
*   **`classroom_chunks` & `youtube_chunks`**: The **Vector Database**.
    *   *Explanation:* When a user uploads a Classroom PDF or YouTube video, we extract the text, chunk it into smaller pieces, and generate a vector embedding (an array of numbers representing meaning).
    *   *Column:* `embedding vector(1536)`. We use the `pgvector` extension to perform semantic search to answer AI queries based on these documents.

### 5. AI Accountability Calls
*   **`study_call_reminders`**: Schedules for voice calls.
*   **`call_sessions`**: Logs of actual Twilio calls made to the user, including the transcript and mood analysis extracted by the AI.

### Database Concepts for Interviews
*   **Primary Keys (PK):** A unique identifier for a row (usually `id UUID`).
*   **Foreign Keys (FK):** A column that references a PK in another table to establish a relationship. (e.g., `user_id` in `notes` references `user_id` in `profiles`).
*   **Indexes:** Added to frequently searched columns (like `user_id` or `scheduled_at`) to massively speed up query performance. `CREATE INDEX IF NOT EXISTS notes_user_set_idx ON public.notes(user_id, set_id);`
*   **Vector Search:** If asked how AI reads documents, explain: "We extract the text, turn it into vectors using an embedding model, store it in Postgres using pgvector, and use a cosine-similarity SQL function to find the most relevant paragraphs when the user asks a question."
